# wg-ss

A single container that joins a **WireGuard peer as a client** and exposes a
**shadowsocks-rust** server as the external entry point. Point any Shadowsocks
client at it and your traffic egresses through the WireGuard tunnel:

```
  SS client ──(shadowsocks + obfs)──▶ ss-server ──▶ container network stack
                                                        │
                                        wg0 (wg-quick, kernel or wireguard-go)
                                                        │
                                    WireGuard peer ──▶ tunnel-side LAN / internet
```

It is the client-side counterpart of [`wireguard`](../wireguard) (which installs
a WireGuard **server** on the host with systemd) and follows the same shape as
[`tailscale`](../tailscale): a `run` host-launcher, a multi-stage `Dockerfile`, a
`docker-entrypoint.sh`, and an externally-supplied secret — here the client
private key. Shadowsocks is installed via the repo's own
[`ss-rust`](../ss-rust) installer, with the `obfs-server` plugin for HTTP/TLS
obfuscation.

## How it works

`ss-server` dials each target **from inside the container**. Whatever the tunnel
routes, SS clients reach — with the default `AllowedIPs = 0.0.0.0/0,::/0` that
is everything, so the container is an SS front door for a VPN exit. Narrow
`--allowed-ips` and it becomes a split-tunnel gateway into a private LAN
instead.

Kernel WireGuard is used when the host has the module; otherwise `wg-quick`
falls back to the bundled `wireguard-go` over `/dev/net/tun`. Both paths need
`--cap-add NET_ADMIN --device /dev/net/tun`, which `run` passes for you — no
`--privileged`, no `/lib/modules` mount.

## Quick start

```bash
# A provider config, or one generated by ../wireguard/wg-client
./run --conf ~/wg0.conf --ss-port 8388

# Read the connection details (auto-generated password is printed here)
docker logs -f wg-ss
```

Discrete values instead of a file:

```bash
./run --private-key "$(cat client.key)" \
      --address 10.0.0.2/32 \
      --peer-key SERVER_PUBLIC_KEY \
      --endpoint vpn.example.com:51820
```

Prefer an env file:

```bash
cp .wg-ss.env.example .wg-ss.env
$EDITOR .wg-ss.env          # set WG_PRIVATE_KEY, WG_ENDPOINT, SS_* ...
./run --env-file .wg-ss.env
```

The rendered config persists in the `wg-ss-state` volume, so a later
`./run` with no config at all reuses it (the log says so).

## Options (`./run --help`)

| Flag | Env | Purpose |
|------|-----|---------|
| `--conf` | — | A WireGuard `.conf` used as-is (mounted read-only at `/config/wg0.conf`) |
| `--private-key` | `WG_PRIVATE_KEY` | Client private key |

| `--peer-key` | `WG_PEER_PUBLIC_KEY` | Server public key |
| `--endpoint` | `WG_ENDPOINT` | Server `host:port` |

| `--dns` / `--no-dns` | `WG_DNS` / `WG_USE_DNS` | Resolver inside the container |
| `--mtu` | `WG_MTU` | Tunnel MTU (default 1420) |
| `--keepalive` | `WG_KEEPALIVE` | `PersistentKeepalive` (default 25) |
| `--table` | `WG_TABLE` | wg-quick routing table, or `off` to route it yourself |
| `--probe-target` / `--no-probe` | `WG_PROBE_TARGET` / `WG_PROBE` | Liveness probe |
| `--ss-port` | `SS_PORT` | Shadowsocks port (default 8388) |
| `--ss-password` | `SS_PASSWORD` | SS password (auto-generated if blank) |
| `--obfs-host` | `SS_OBFS_HOST` | obfs masquerade host (client-side hint) |
| `--bind` | — | Host bind address for the published port |
| `--env-file` | — | KEY=VALUE file of the above |
| `--state-volume` | — | Volume for `/etc/wireguard` (default `wg-ss-state`) |
| `--build` | — | Force image rebuild |

Env-only knobs: `SS_METHOD`, `SS_MODE`, `SS_OBFS`, `WG_PROBE_INTERVAL`,
`WG_PROBE_FAILURES`, `WG_MAX_RESTARTS`, `WG_HANDSHAKE_TIMEOUT`, `WG_CONFIG`.
See `.wg-ss.env.example`.

## Config sources

Checked in this order:

1. `/config/wg0.conf` — a file mounted with `--conf`.
2. `WG_CONFIG` — a whole config in one env value, base64 (`base64 -w0 wg0.conf`)
   or raw with `\n` escapes.
3. `WG_PRIVATE_KEY` + `WG_ADDRESS` + `WG_PEER_PUBLIC_KEY` + `WG_ENDPOINT`,
   rendered into a config.
4. Whatever the `wg-ss-state` volume kept from the previous run.

A `DNS=` line in sources 1–2 is honored: the entrypoint takes it out of the
config and writes `/etc/resolv.conf` itself (see Gotchas).

## Liveness probe

A ping through the tunnel is the only signal that separates *idle* from *dead* —
WireGuard only rekeys when data flows, so a healthy but quiet tunnel has an old
handshake. Every `WG_PROBE_INTERVAL` seconds the entrypoint pings
`WG_PROBE_TARGET` through `wg0`; after `WG_PROBE_FAILURES` consecutive misses it
bounces the interface in place (re-applying routing and DNS), and after
`WG_MAX_RESTARTS` failed rounds it exits so docker's restart policy takes over.
`ss-server` dying always ends the container.

The default target is `1.1.1.1` for a full tunnel, otherwise the first host of
`AllowedIPs`. That is a guess, so it is verified once at startup: if it never
answers, the probe is disabled rather than bouncing a working tunnel forever
(both outcomes are logged).

## Client configuration

Any Shadowsocks client works. Match what the container logs at startup:

- **server**: the host's public IP
- **server_port**: `SS_PORT`
- **password**: from the logs (or your `SS_PASSWORD`)
- **method**: `chacha20-ietf-poly1305`
- **plugin**: `obfs-local` with `obfs=http;obfs-host=<SS_OBFS_HOST>` (omit if `SS_OBFS=none`)

## Gotchas

- **No `--host-net`.** A full-tunnel `AllowedIPs` in the host's network
  namespace would reroute the whole host, not just this proxy. Use
  [`wireguard`](../wireguard) if that is what you want.
- **`/proc/sys` is read-only in a container**, so `wg-quick`'s
  `sysctl -q net.ipv4.conf.all.src_valid_mark=1` fails — and since `wg-quick`
  runs under `set -e`, that aborts the whole bring-up. `run` passes
  `--sysctl net.ipv4.conf.all.src_valid_mark=1` and the image ships a `sysctl`
  shim that accepts a write whose value is already in effect. Hand-rolled
  `docker run` commands need that flag too.
- **Return-path routing.** With a default-route `AllowedIPs`, `wg-quick` installs
  `ip rule` entries that pull *all* traffic into the tunnel. Replies to *inbound*
  SS connections would leave via `wg0` with the wrong source address and every
  session would hang right after the TCP handshake. The entrypoint adds
  `ip rule from <container-addr> lookup main pref 90` ahead of them. Locally
  *originated* connections still take the tunnel, because their source is not
  chosen until after the route lookup.
- **`wg-quick`'s `DNS=` needs resolvconf** and rewrites `/etc/resolv.conf`, which
  is a bind mount in a container. The entrypoint strips `DNS=` and writes
  `/etc/resolv.conf` in place instead (addresses only — search domains in a
  `DNS=` line are dropped). Set `WG_USE_DNS=false` to keep docker's resolver.
- **DNS ordering.** The resolver is switched *after* the tunnel is up, so a
  hostname `Endpoint` still resolves with docker's DNS at bring-up time.
- **`docker --env-file` does NOT strip inline `#` comments** — everything after
  `=` is literal. The entrypoint `_clean()`s the constrained fields defensively,
  but `.wg-ss.env` must still keep comments on their own lines.
- Secrets (`WG_PRIVATE_KEY`, `WG_PRESHARED_KEY`, `WG_CONFIG`, `SS_PASSWORD`) are
  runtime `-e` only, never `ENV` in the Dockerfile.
- `wireguard-go` is not packaged by Alpine, so the builder compiles it from
  `golang.zx2c4.com/wireguard` (main package at the module root; the binary is
  renamed to `wireguard-go`, which is what `wg-quick` looks for). Upstream's
  `0.0.x` git tags are not on the Go module proxy — pin
  `WIREGUARD_GO_VERSION` to a pseudo-version if you need reproducibility.

## Files

| File | Purpose |
|------|---------|
| `run` | Host launcher: builds the image, runs the container with tun + published SS port |
| `install` | `curl`-pipeable installer (fetches the build context, installs docker if missing) |
| `Dockerfile` | Multi-stage build (ss-rust + wireguard-go → Alpine runtime) |
| `docker-entrypoint.sh` | Renders the config, `wg-quick up`, fixes routing/DNS, runs ss-server, supervises both |
| `.wg-ss.env.example` | Documented env template |
